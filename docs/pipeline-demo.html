zf-approx: what goes in, what gets processed

The whole repo is one one-way procedure: names → indices → names. This page walks one example through every stage. All states below were produced by running the shipped code (commit 88d1196) — nothing is drawn by hand.

Reading guide. §0 is the entire pipeline in one figure. §§1–4 walk the house graph through it (input → translation → loop → output). §5 shows three more inputs (C5, disconnected, isolates). §6 maps the files. Skim §0 and §4 for the shape; read §§2–3 for the machinery.

0 · The pipeline in one figure

One function is the only export: zf.zero_forcing_set(graph, bags). The translation layer is the only place that touches external formats; the core never sees a name, and the outside never sees an index. The core is unchanged from rounds 1–5.

1 · What goes in

The graph (NetworkX, nodes = names)

The house: square 1-2-3-4-1 plus roof vertex 5 joined to 2 and 3. Edges: [[1, 2], [1, 4], [2, 3], [2, 5], [3, 4], [3, 5]].

The bags (a path decomposition — not nice)

{1, 4}{1, 3, 4}{1, 2, 3}{2, 3, 5}

Width = max|bag| − 1 = 2. Every edge lies in some bag (D1); each vertex’s bags are contiguous (D2); every vertex appears. That is the whole contract — suitability is the caller’s responsibility; nothing is validated (your ruling).

Two bag-to-bag changes move two vertices ({1,3,4}→{1,2,3} and {1,2,3}→{2,3,5}), so this is not a nice decomposition. The layer must fix that.

Step B · _to_nice — forget-first, width-preserving

The input bags, with the single-vertex steps the layer inserts (∅ ends padded; empty/duplicate bags dropped):

∅+1+4{1, 4}+3{1, 3, 4}−4+2{1, 2, 3}−1+5{2, 3, 5}−2−3−5∅

The resulting nice bag sequence (each step adds or removes exactly one vertex; every input bag appears verbatim, so D1/D2 and the width survive):

∅+1{0}+4{0, 3}+3{0, 2, 3}−4{0, 2}+2{0, 1, 2}−1{1, 2}+5{1, 2, 4}−2{2, 4}−3{4}−5∅

Why forget-first: intermediate bags stay subsets of the old bag (during forgets) or the new bag (during introduces) — width preserved. Introduce-first could inflate a bag to |X_i ∪ X_{i+1}|. This is the paper’s cited transformation (Bodlaender–Kloks, Lemma 13.1.3). Consecutive bags with empty intersection (disconnected graphs) pass through ∅ — see §5.

3 · The core — loop L1–L8 with the three tricks

blue in the region (X_t ∪ X_z) outside, assumed blue — trick [L6c] white fort (white at fixation)

The loop scans z forward from t. [L3] introduce steps — and forgets of vertices already in X_t — keep W = ∅, so they skip closure entirely. Closure runs on the full graph with every outside vertex assumed blue [L6c]; no induced subgraph is ever built. S is never maintained [L6b] — it is read off the arcs once, at the end.

Four closure calls (z = 4, 6, 8, 9); five steps skipped by [L3]. At z = 9 the bag is {5}: vertex 5 has two white neighbours (2 and 3), nobody can force — the white set {1,2,3,4} is a fort (outside vertex 5 touches it twice, not once).

L6 — collect the fort, build the arc set

L6a: F ← F ∪ {1,2,3,4}. L6c: run closure again from X_t ∪ X_{z−1} = {3,5} on the full graph (outside = ∅ now; the region is all of V). Forcing sequence, min-index canon:

  1. 5 forces 2 — 5’s only white neighbour is 2 (white set was {1, 2, 4})
  2. 2 forces 1 — 2’s only white neighbour is 1 (white set was {1, 4})
  3. 1 forces 4 — 1’s only white neighbour is 4 (white set was {4})

These arcs are merged into A (which was empty): 5→2 · 2→1 · 1→4. L6d: delete arcs whose head lies in X_z = {5} — none (5 is a tail). L6e: t ← 9.

Inside closure (the B-F-H count engine)

Each blue vertex keeps a count of its white neighbours; a vertex with count 1 is eligible and forces its unique white neighbour; the count of each blue neighbour of the newly-blued vertex drops by 1. A min-heap picks the smallest eligible index each step (the paper’s example canon, tex:L621). At z = 9 the call starts from {5}: 5 has two white neighbours, no vertex is eligible, the process fixates immediately — white = {1,2,3,4}.

Outer iteration 2 — t = 9, X_t = {5}

zstepactionblue given to closureW
10−5[L3] skip — forget inside X_t——

z = 10 = k+1: forgetting 5 ∈ X_t changes nothing — the second [L3] skip. W stays ∅, so the loop finishes (L7 adds no arcs: everything is already blue from V).

L4 — the reversal that makes S appear

⟲
A.reverse()

The scan built the chain pointing into the processed region (5→2→1→4). Reversing it points the chain out of the sources: 4→1→2→5. L8 / [L6b]: S = sources(A) — the vertices with no in-arc — computed once, here: {3, 4} (3 is idle; 4 starts the chain).

4 · What comes back — ZFResult in the original names

Green double ring = S (zero forcing set). Amber ring = the fort. Purple arrows = the forcing arcs A.

forts  = ({1, 2, 3, 4},)

Check the forcing from S = {3,4}: 4 forces 1 (its only white neighbour), 1 forces 2, 2 forces 5 — everything blue. The fort {1,2,3,4} is valid: outside vertex 5 has two neighbours in it, never exactly one.

5 · Three more inputs (same one-way procedure)

c5 n=5, width 2

bags in: {0, 1}{0, 1, 2}{0, 2, 3}{0, 3, 4}
S = {0, 4} · forts = {0, 1, 2, 3} · arcs = 0→1 · 1→2 · 2→3
guarantee: 2 ≤ (2+1)·1 = 3 ✓

Your C5 from spec2, now through the full algorithm: one fort (the path 0-1-2-3), and the chain 0→1→2→3 forces the rest from S={0,4}.

two-triangles n=6, width 2

bags in: {a, b}{a, b, c}{b, c}{d, e}{d, e, f}{e, f}
S = {b, c, d, f} · forts = {a, b}; {d, e} · arcs = b→a · d→e
guarantee: 4 ≤ (2+1)·2 = 6 ✓

Disconnected: the bags of the two components have empty intersection, so the width-preserving nicification passes through an empty intermediate bag. The core replays ops without D3 checks and handles it: two forts, one per component.

two-isolates n=2, width 0

bags in: {a}{b}
S = {a, b} · forts = {a}; {b} · arcs = (none)
guarantee: 2 ≤ (0+1)·2 = 2 ✓

Edge case: isolated vertices must lie in some bag (suitability). Each is its own fort and must be in S; the guarantee is tight: 2 ≤ (0+1)·2.
